Upgrade to Inmor 0.6.0
======================

Inmor 0.6.0 was released on November 26, 2026. This guide covers upgrading
from 0.5.1.

Before rollout
--------------

* If you use the bundled PostgreSQL 14 or 15 database, follow
  :doc:`../postgresql-upgrade` before starting the 0.6.0 stack.
* Back up Redis and retain the existing data through the upgrade. The
  migration imports digests for trust mark JWTs still in PostgreSQL. For
  older JWTs already replaced or cleared, the issuance history may exist
  only in the Redis set ``inmor:tm:alltime``.
* If clients use ``/resolve`` with an external trust anchor, provision its
  public keys before rollout. The local anchor uses its existing public keys.
  See :ref:`resolver-trust-anchors`.
* Review Subordinate Statements issued by your anchor and intermediates.
  Check that each host under a ``naming_constraints`` rule is in scope.
  Keep legacy URL subtree rules if you rely on path or port restrictions.
  See :ref:`resolver-naming-constraints`.
* Omit unused ``metadata_policy`` and ``metadata_policy_crit`` claims.
  Reissue statements containing empty policy objects, malformed operators
  or unsupported critical extensions, and remove subordinate-only claims
  from Entity Configurations. Check that policies from different superiors
  have compatible operands. See :ref:`resolver-metadata-policy`.
* Check forced metadata on existing subordinates before renewal. Every
  top-level key must name an entity type and its value must be an object.
  The Admin applies the configured policy after those overrides.
* Check that resolve clients read the subject's ``trust_chain`` from the signed
  payload. Earlier versions also copied it into the JWS header. In 0.6.0
  the chain appears only in the payload.
* Identify the people who manage the federation through the Admin UI and the
  accounts that own keys used by automation. With the current Admin checkout,
  run ``python manage.py apikey list --all`` to see key owners. Confirm that
  you can sign in to Django admin as an active superuser to grant access.
* Check the signing algorithms used by your federation peers. Admin now
  applies the Trust Anchor's allowlist during onboarding, self-verification
  and renewal. Peers using ``RS384``, ``RS512``, ``PS384``, ``PS512`` or HMAC
  must switch to a supported algorithm before rollout. Each statement's
  ``kid`` must identify one verification key, and JWT payload member names
  must be unique. See :ref:`signature-algorithms` for the accepted algorithms.
* Existing signing keys and issued statements retain their format. Adopting
  post-quantum signatures is optional. If you plan to rotate to one of the
  new algorithms, confirm peer support first. See :ref:`pqc-signing-keys`.

Deploy and grant operator access
--------------------------------

1. Pause Admin writes and scheduled renewals. Deploy the 0.6.0 Trust Anchor
   and all Admin processes together with the matching
   templates and frontend, if used. Keep the existing signing keys and MFA
   encryption key. The Admin container runs Django migrations at startup.
   For a source deployment, build the Trust Anchor with ``cargo build
   --release --locked``. From ``admin/``, run ``uv sync --locked`` and
   ``uv run python manage.py migrate`` with the deployment's settings.
   In Compose, check the applied migrations::

      docker compose exec -T admin python manage.py showmigrations entities

   Confirm that ``0004_manage_federation_permission``,
   ``0005_pendingpublication`` and ``0006_issuedtrustmarkhash`` each show
   ``[X]``. Replace scheduled renewal commands with the 0.6.0 version before
   resuming writes.

2. In Django admin (``/admin/``), open **Groups**, create or edit an operator
   group, and add **Can manage the federation**
   (``entities.manage_federation``). Under **Users**, assign the
   group to each intended operator and API key owner. Active superusers
   already have the permission. Service accounts need no staff status.
   Automation can keep using its existing keys. Each key uses its owner's
   current permissions on every request.

3. Provision future accounts through your administrator. Public signup is
   closed. Staff sign in through allauth and complete any enrolled MFA
   challenge. Existing sessions keep their expiry. If staff must authenticate
   again at cutover, invalidate their existing sessions. See :doc:`../guides/mfa`
   for enrollment and recovery.

Verify before resuming automation
---------------------------------

* From the management network, make a read-only request using an existing
  operator key. Set ``ADMIN_URL`` to the HTTPS origin of your Admin service
  and ``INMOR_API_KEY`` to that key::

     curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
       --header "X-API-Key: $INMOR_API_KEY" "$ADMIN_URL/api/v1/trustmarktypes"

  Expect HTTP 200. HTTP 403 with a valid key means its owner lacks the
  operator permission. HTTP 401 means the key failed authentication. See
  :doc:`../guides/api-keys` to check its status.
* In a fresh browser session, open ``/admin/`` as a staff member with an
  enrolled factor and complete the MFA challenge. Open the Admin UI as an
  authorized operator and confirm that it lists the expected subordinates.
  If the frontend runs behind a custom proxy, check login, MFA and logout
  through its public origin. See :doc:`../guides/admin-ui` for the proxy paths.
* Run ``docker compose exec -T admin python manage.py retry_publications``
  and check that it exits successfully. Schedule the command periodically.
  If Redis delivery fails after a database commit, the public endpoints can
  still serve the previous state until the retry succeeds. See
  :doc:`../guides/management-commands`.
* Retrieve ``/.well-known/openid-federation`` from the Trust Anchor and verify
  its signature with your federation client. Resolve a known subordinate and
  confirm that the chain still leads to the expected Trust Anchor. Repeat
  for each external anchor your clients request.
* Resolve a leaf with a known policy and inspect the signed metadata and
  chain. In staging, also check a leaf for which every path violates a
  naming or policy rule. Expect HTTP 400 with ``invalid_trust_chain``.
  If a valid alternate path exists, expect HTTP 200 and that path's metadata.
